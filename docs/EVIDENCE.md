# Evidence

What counts as a proof in this project, and what does not.

## The standard

A claim is **evidence** when it is:

1. **reproducible** — anyone with a lawful copy of the disc can redo it;
2. **pinned** — it names the exact input, by hash, and the exact tool, by
   hash where the tool is a binary;
3. **measured** — it reports what was observed, not what is expected;
4. **falsifiable** — it states the observation that would refute it.

## Accepted evidence

| Claim | Evidence required |
| --- | --- |
| the disc identity | the SHA-1 and SHA-256 of the image, recomputed from a lawful copy |
| the container layout | the offsets, read by `tools/psp_formats.py` and shown by a test on synthetic data |
| the asset inventory | `config/disc/pack_index.tsv`, regenerated by `tools/disc_inventory.py` |
| the absence of code in the assets | the prologue scan and the address scan described in `docs/FORMATS.md` |
| a toolchain profile | a measured cause, a known provenance, a regression control |
| a function body | the compiled bytes equal to the retail bytes at the measured offset, byte for byte |
| a placement | the body linked at that offset, and the same body proved elsewhere |
| the complete program | the whole program equal to the retail hash |

## Refuted evidence

These are the usual failure modes, listed because they are the usual
failures:

* **the compiler agrees with itself.** Two compilers producing the same
  wrong bytes are not evidence of anything.
* **a masked comparison.** Comparing bytes with the relocation fields
  masked hides exactly the differences that matter.
* **a visual match.** A disassembly that *looks* like the source is a
  hypothesis.
* **a name.** A plausible function name is a hypothesis until a caller, a
  symbol, a string or a data reference supports it.
* **the first difference.** Parking a body at "the first difference" is
  honest; parking it at "the first difference, probably" is not.

## The visibility rule

This project has one rule that its PS2 siblings do not need:

> **Nothing about a function may be claimed before the decrypted executable
> exists locally and has been measured.**

The decryption needs a PSP implementation and a lawful copy of the disc.
Both stay on the contributor's machine. The *structure* that comes out of it
— sections, symbols, sizes, hashes, counts — is research metadata, and that
is what the repository publishes.

The corollary is equally strict: **no instruction listing, no disassembly and
no extracted module is ever committed**, whether it came from the disc or
from the decryption step.

## Provenance of the formats

The container layouts in `docs/FORMATS.md` were read from the pinned disc by
the readers in `tools/psp_formats.py`, and each reader is tested against
synthetic data in `tests/test_tools.py`. Where a meaning is not
established, the document says so instead of guessing: the five header
words of `Pack`, the payload boundary of `~PSP`, and the member table of
`PSAR` are all listed as open.

Where a first implementation was wrong, the correction is recorded rather
than hidden — see the note on the `PARAM.SFO` value offsets.
